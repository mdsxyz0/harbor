# تحليل خدمات Harbor وروابطها

تاريخ الفحص: 20 أكتوبر 2026. هذا تقرير قراءة للمصدر وفهارس `docs/harbor-audit/` فقط؛ لم تُجر اختبارات أو بناء أو نشر. لا يحتوي التقرير على قيم مفاتيح أو معرّفات عملاء.

## خلاصة التشغيل والملكية

المستودع عميل Harbor، وليس مستودع خدماته. بعد فحص الملفات المفهرسة والمسارات، لم أجد شيفرة لخدمات API أو موقع/أصول التحديث أو مزامنة الملفات الشخصية في المستودع. الاستثناء التنفيذي الواضح هو مرحّل Together الموجود في `src-tauri/relay/worker.js`: عامل Cloudflare مع Durable Object للغرف وendpoint لـ`/proxy` بقائمة مضيفين مسموح بها. لا توجد معه ملفات نشر مثل `wrangler.toml` أو تعريف binding أو إعدادات DNS وبيئة؛ وجود الشيفرة لا يثبت أن الخدمة منشورة أو أن حسابها تحت سيطرتنا.

إذن تغيير الروابط وحده لا ينقل الخدمة. يلزم توفير تنفيذ/استضافة وبيانات متوافقة لكل واجهة يعتمد عليها العميل قبل توجيه الإصدارات إليها. يضم نطاق `harbor.site` وظائف مستخدمين ومزامنة ومحتوى ثابتاً وبيانات تثبيت وتحديث؛ تعطّل أي مسار منها قد يظهر كفقد مزايا أو فقد وصول للمستخدم.

الجرد الحرفي يسجل أيضاً مرجعاً عاماً لـ`https://harbor.site` في فحص الاتصال (`src-tauri/src/torrent_engine/netcheck.rs`) وصورة الشعار في README وبيانات Flatpak. هذه مراجع منفصلة عن API؛ ينبغي تصنيفها عند الاستبدال. لا تعتبر URLs التي تحتوي `harbor.site` داخل الترجمة أو الوثائق نقاط اتصال تشغيلية تلقائياً.

### روابط الشركاء وOAuth خارج نطاق خدمات Harbor

- Stremio login يمرر callback loopback مؤقتاً `http://127.0.0.1:{port}/cb` (`src/lib/stremio-auth.ts` مع listener في Rust). ليس callback على harbor.site. احتفظ باسم التطبيق وبالمخططين `harbor` و`stremio` في إعداد deep-link ومعرّف التطبيق `app.harbor`؛ تغييرها قد يكسر ربط الملفات/الروابط وتخزين إعدادات سطح المكتب.
- MAL يفتح authorize على `myanimelist.net` ويستخدم `${HARBOR_MAL_BASE}/mal/` كـredirect، ثم يبدل الرمز عبر `/api/mal/token`. يلزم تسجيل redirect URI الجديد في لوحة MAL والتأكد من تدفق PKCE وتطابق callback، وإلا يفشل تسجيل الدخول.
- AniList يستخدم authorize وPIN callback لدى AniList، ثم يرسل الرمز إلى endpoint Harbor تحت `/v1/anilist/token`. تغيير proxy يتطلب تنفيذ exchange آمناً وإبقاء callback لدى AniList كما هو.
- Trakt يستخدم device authorization؛ التطبيق يتصل بـTrakt ويستخدم proxy Harbor لـtoken وdevice-token. لا يوجد redirect خاص بـHarbor، لكن تظل سياسة المفاتيح/الأسرار على الخادم مهمة.
- Simkl يستخدم PIN/device flow مع API Simkl مباشرة، و`/api/simkl/ratings` عبر Harbor للبروكسي/التقييمات. لا تنقل هوية تطبيق Simkl أو واجهته الخارجية ضمن نقل النطاق.

معرّفات تطبيقات OAuth الظاهرة في المصدر قيم public client وليست أسراراً، لكنها لا ينبغي نسخها إلى التقرير أو افتراض أن ملكية حسابات التسجيل أو الصلاحية انتقلت. أسرار Trakt/PIN وrefresh/access tokens قيم مستخدم/اعتماد؛ يمنع تسجيلها أو ترحيلها ضمن متغيرات بناء عامة.

## إعدادات التحديث والتوقيع

`src-tauri/tauri.conf.json` يثبت endpoint المكوّن الأصلي `https://harbor.site/updates/latest.json` ويحتوي public updater key. أبقيت قيمة المفتاح خارج هذا التقرير. تغيير `VITE_HARBOR_API_BASE` لا يغير بالضرورة هذه القيمة native: `@tauri-apps/plugin-updater` يأخذ feed/key من إعداد Tauri المضمّن في الحزمة. بالتوازي، `src/lib/updater/use-update.ts` يجلب `latest.json` ويختار قناة beta برأس `x-harbor-channel`، و`src/lib/updater/versions.ts` يجلب `versions-beta.json`، و`release-notes.ts` يجلب `release-notes.json`. لذلك يلزم تحديث TS وTauri config/feed ومانيفستات القنوات وروابط أصول كل منصة معاً.

الإصدارات المثبتة بالفعل ستستمر في سؤال عنوان feed القديم المضمّن. بما أن المفتاح الخاص القديم غير متاح بحسب وصف المهمة، فلا يمكن افتراض توقيع حمولات جديدة تقبلها تلك النسخ. الخطة الآمنة هي نشر إصدار انتقال موقّع بالمفتاح القديم فقط إن أمكن استعادته، وإلا تقديم حزمة التثبيت الجديدة على أنها تتطلب تثبيتاً أولياً/إعادة تثبيت، ثم بدء قناة التحديث بمفتاح جديد. لا تُحذف أو تُستبدل المفاتيح القديمة من إعدادات المستخدم محلياً ولا يُدّعى توافق التحديث الذاتي من دون إثبات سلسلة التوقيع. يجب أن يكون لكل stable وbeta feed/manifest وقواعد توزيع مقصودة وواضحة؛ لا تجعل رأس beta وحده يحدد رابط feed native.

## الإعدادات المحلية والهجرة

الروابط العامة في `endpoints.ts` إعدادات build-time من متغيرات Vite، وليست حقولاً للمستخدم في `Settings`. حقول الاتصال المخصصة الفعلية التي ينبغي صونها تشمل `remoteStreamServerUrl` و`togetherRelayUrl` وبيانات اتصال Cloudflare التي يضيفها المستخدم لتشغيل مرحّله، ومفاتيح/جلسات مزودي المحتوى. توجد مفاتيح `harbor.settings`, `harbor.settings.shared`, و`harbor.settings.<profile>` مع ترحيل legacy داخلي بين إعدادات الملف الشخصي؛ قارئ الإعدادات يدمج القيمة القديمة مع defaults ويعالج مفاتيح سابقة (`src/lib/settings/load.ts`, `src/lib/settings/profile-store.ts`). لا تستبدل JSON كاملاً عند تحديث عنوان Harbor ولا تنشئ migration تسقط الحقول غير المعروفة.

إذا كان التحول مجرد نقل API داخل تطبيق سطح المكتب مع الحفاظ على `identifier: app.harbor`، فالأصل أن ملفات بيانات التطبيق والمفاتيح الحالية تبقى على الجهاز؛ حدّث إعداد الخدمة الافتراضي فقط. إذا تغير معرّف التطبيق أو مصدر واجهة الويب، فهناك احتمال أن تظهر مساحة تخزين مختلفة. كما أن تخزين الويب مقيد بالأصل؛ الموقع الجديد لا يستطيع قراءة localStorage من harbor.site تلقائياً. صمم استيراداً صريحاً/تصديراً احتياطياً مع معاينة قبل الاستبدال عند الحاجة، وحافظ على مفاتيح custom endpoints والرموز الخاصة، ولا تمسحها عند تعذر الاتصال بالخدمة القديمة. أي انتقال تلقائي بين المواقع يحتاج جسراً موثوقاً ومحدوداً أو إدخال المستخدم لملف تصدير؛ لا تعتمد على بقاء نطاق قديم تحت سيطرة طرف آخر.

## خطة نقل مقترحة

1. **تثبيت التوافق وجرد العقود:** اصنع سجل خدمة واحداً يربط كل ثابت/مضيف بمسارات الطلبات وطريقة HTTP ونموذج البيانات والأصل المستضيف (ثابت/وظيفي/WebSocket) ومن يملك قاعدة بياناته/أسراره. ابدأ بمصفوفة الفروع العشرين، وأضف الفئات القادمة من beta عند استيراد كل ميزة. استخرج كذلك المسارات المركبة من استدعاءات source، لا الجرد الحرفي وحده.
2. **توفير خدمات نملكها قبل تغيير العملاء:** أنشئ/انقل backend المستقل لـ`themes/api`, `bugs`, `sync`, proxies، static feeds/assets وweb invite على حسابات وأسماء نطاق نملكها. وحّد عقود JSON وCORS وحجم الملفات/الحدود والمصادقة والاحتفاظ والنسخ الاحتياطي. لا توجد هذه implementations هنا؛ لا يبدأ تبديل العملاء حتى تتوفر البيئات وعقود التوافق والبيانات والاختبارات في المستودعات/الخدمات المالكة.
3. **مركزة إعدادات البناء على مستوى كل الفروع:** حدّث كل literals المتبقية ومصادر Rust/Tauri وقوالب manifests/README بالتوازي مع `endpoints.ts`. اجعل resolver يوجه لكل خدمة بوضوح، وتأكد أن runtime endpoints لا تُفترض قابلة للتحويل بواسطة Vite env في native updater أو في URLs المنسوجة داخل إعدادات أخرى. لا تنسَ مناداة `pub.harbor.site` المباشرة ومقارنة المضيف في `relay-version.ts`.
4. **تثبيت OAuth والبيانات:** سجل redirect الجديد في MAL، وراجع token-exchange endpoints لتدفقات AniList/MAL/Trakt؛ اترك callbacks الخاصة بـStremio/AniList/Simkl الخارجية كما هي ما لم يتطلب التسجيل غير ذلك. خطط لنقل قواعد المستخدمين ومفاتيح التوقيع والملفات والـfeeds دون تضمين أسرار في frontend. قرر مصير الرموز: المحافظة عليها إن كانت صلاحياتها ونطاقاتها صالحة، أو إعادة تفويض واضحة بدلاً من تسريب/نسخ credentials.
5. **التحديث كمسار إصدار مستقل:** تحقق من إمكانية توقيع إصدار انتقال بالمفتاح السابق. عند عدم توفر private key، أطلق installer/حزمة جديدة تتطلب إعادة تثبيت للمستخدمين الحاليين. بعد ذلك طابق native Tauri endpoint وpublic key مع feed الجديد، وأصدر manifests منفصلة لـstable وbeta وأصول المنصات، ثم راقب مجموعة تجريبية قبل تعميمها.
6. **انتقال تدريجي ثم إيقاف القديم:** وفّر redirect/compatibility API إن كان النطاق والبيانات القديمان تحت الملكية؛ وثّق أن redirect HTTP لا يكفي لـPOST/WebSocket/OAuth أو للطلبات الموقعة. قدّم stable كقاعدة، وأدخل ميزات beta في دفعات مع endpoints المطلوبة وعقودها، ثم أوقف المضيف القديم بعد قياس الطلبات ونسبة نجاح الدخول والمزامنة والتحديث، مع خطة rollback للخدمات والعميل.

## مخاطر القبول

- **خدمات غير موجودة هنا:** لا يمكن إثبات توفرها أو ملكيتها أو نقل بياناتها من هذا repo. يلزم دليل من مستودع الخدمة/حساب الاستضافة، وخطة backup/restore وملاك تشغيل.
- **توافق البروتوكول:** رد JSON أو أسماء المسارات التي يتوقعها العميل قد تغيّرت عبر beta؛ النقل المباشر قد يجعل النسخ القديمة أو الميزات الجديدة تتعطل بصمت.
- **تسجيل الدخول:** redirect غير مسجل، CORS خاطئ، أو token exchange ينفذ في العميل قد يكسر OAuth أو يكشف أسراراً.
- **التحديث:** تغيير feed دون المفتاح المتوافق يمنع تثبيت التحديث؛ وحزمة تعمل عبر التثبيت اليدوي ليست دليلاً على عمل updater. اختلاف stable/beta يزيد احتمال نشر manifest خاطئ.
- **التخزين المحلي:** تغيير origin/identifier أو استبدال المستند كاملاً قد يفقد تفضيلات الملف الشخصي، endpoints التي أدخلها المستخدم، مفاتيحه المحلية، أو جلسات مزودي الخدمة. اترك التخزين القديم عند فشل الترحيل ووفّر استعادة قابلة للفهم.
- **المرحّل:** ملف العامل الموجود لا يكفي للنشر؛ لا تظهر إعدادات الحساب أو DNS/bindings أو المراقبة. قائمة البروكسي المسموحة وrate-limit وبيانات WebSocket والسجلات تحتاج مراجعة أمنية وتشغيلية قبل تملك الخدمة.

## حدود الإثبات

هذا استنتاج من النصوص المفهرسة ومصدر الفرع المحلي `coxde/windows-stable-installer` ومقارنة refs `main`, `stable-branch`, `beta-branch` المتاحة في 20 أكتوبر 2026. لم أتحقق من DNS أو استجابة الشبكة أو لوحات OAuth أو مخازن المستخدمين أو صلاحية المفاتيح أو نشر العامل، ولم أبن التطبيق. يلزم مراجعة شيفرة الخدمات والحسابات المالكة قبل تحويل أي endpoint.
