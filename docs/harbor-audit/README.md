# خطة استقلال Harbor وتوحيد فروعه

تاريخ الدراسة: 20 أكتوبر 2026. الاتجاه الذي اختاره المستخدم: نسخة مستقرة للمشاهدة، ثم إضافة ميزات البيتا تدريجيًا. أُجّل شراء النطاق، وأُجيز إنشاء خادم جديد على Cloudflare. لم يُجز دمج جميع الفروع أو حذفها أو تحويل كل خدمات التطبيق دفعة واحدة.

## النتيجة

نعتمد `stable-branch` أساسًا للتطبيق، وننقل إليه إصلاح بناء Windows من `coxde/windows-stable-installer`. نوحّد ملكية الخدمات وإعداداتها بين الفروع مع إبقاء اختلاف الميزات. نبدأ بخادم Cloudflare مستقل، ثم ننفذ الخدمات التي يحتاجها إصدارنا تباعًا. استبدال اسم المضيف وحده لا يعيد قاعدة بيانات أو ملفات أو OAuth أو توقيع تحديثات محذوفة.

فُحصت رؤوس **20 فرعًا** قبل إنشاء فرع هذا العمل `coxde/owned-services`. سجل الفحص يتضمن **2059 سطرًا مطابقًا** و**74 عنوان URL حرفيًا مختلفًا** وستة أسماء مضيفات. تشمل الأرقام التوثيق والترجمات والبيانات الثابتة، ولا تعني 2059 طلب شبكة. لا تشمل قائمة URL الحرفية المسارات المركبة من ثوابت؛ لها فهرس مستقل، وتشرح مجموعاتها دراسة الخدمات.

الحصر يخص الكود والبيانات الموجودة في هذه اللقطات. لا يمكن استخراج كل URL قد يرجعه خادم محذوف أو يدخله المستخدم لاحقًا، ولا استعادة محتوى الأصول المحذوفة من مجرد أسمائها. يشمل الحصر البريد `bugs@harbor.site` أيضًا، رغم أنه ليس مضيف خدمة مستقلاً.

## النطاقات والبدائل المقترحة

الأسماء في عمود البديل أدوار إعداد، وليست نطاقات مشتراة أو خدمات جاهزة. لا نضع نطاقًا تجريبيًا في التطبيق ثم ندّعي اكتمال النقل.

| الأصل القديم | ما يعتمد عليه | البديل الذي نملكه |
|---|---|---|
| `harbor.site` | واجهات الحساب والثيمات والمجتمع؛ ملفات الكتالوج والصور؛ OAuth proxies؛ التحديثات والنموذج الصوتي | فصل `apiBase` و`assetsBase` و`updatesBase` و`modelBase`، حتى لو تشاركت الاستضافة أولًا. |
| `bugs.harbor.site` | البلاغات والملاحظات وتقارير الإعلانات وتبادل AniList | `reportsBase` و`oauthBase`؛ نفصل الأسرار ومسارات تبادل الرموز عن استقبال المرفقات. |
| `sync.harbor.site` | قاعدة توقيت الترجمة؛ ومزامنة الملفات الشخصية في beta | `subtitleSyncBase` و`profileSyncBase` مستقلان. لا نفترض أن بياناتهما أو بروتوكولهما واحد. |
| `app.harbor.site` | صفحة فتح دعوات المشاهدة الجماعية | `webJoinBase` لصفحة دعوة فعلية تدعم معاملات العميل. |
| `pub.harbor.site` | اتصال WebSocket للمشاهدة الجماعية | `publicRelayUrl` لخادم متوافق مع بروتوكول إصدار العميل. |
| `www.harbor.site` | الموقع والتوثيق | صفحة المشروع أو موقعنا لاحقًا. |
| `bugs@harbor.site` | البريد وروابط الدعم في الواجهة | رابط Issues في مستودعنا أولًا؛ بريد دعم نملكه عند توفره. |

يمكن تشغيل Worker بعنوان `workers.dev` قبل امتلاك نطاق. ويملك الحساب المتصل نطاقًا فرعيًا جاهزًا؛ لا نغيّر إعداداته العامة أو نلمس العمال الموجودين فيه. المرحلة الحالية تنشئ عاملًا جديدًا باسم `harbor-services` فقط. توصي Cloudflare باستخدام نطاق مخصص للإنتاج طويل الأجل؛ نؤجل ربطه إلى قرار المستخدم. [توثيق workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)

## ما ننفذه الآن وما يؤجّل

الخادم الأساسي يوفّر `/health` و`/v1/config` فعليًا، ويعلن أن بقية القدرات غير متاحة. لا يستقبل حسابات أو كلمات مرور أو رموز OAuth أو مرفقات، ولا يقدّم استجابات نجاح صورية لخدمات غير مبنية. لا نوجّه العميل إليه بوصفه بديلًا لكل خدمات المطور قبل تنفيذ عقودها.

نُشر هذا الأساس على [harbor-services.xyz7.workers.dev/health](https://harbor-services.xyz7.workers.dev/health)، وتتوفر [خريطة القدرات](https://harbor-services.xyz7.workers.dev/v1/config). اجتازت الشيفرة ثماني مجموعات اختبارات عقود، ثم اجتاز العنوان المنشور فحوص HTTPS من GitHub Actions. دليل المراجعة `ff69655c` في [تشغيل التحقق](https://github.com/mdsxyz0/harbor/actions/runs/39469033878). لم تتغير عناوين العميل في الفروع الأخرى؛ نقلها مرحلة مستقلة موضحة أدناه.

| الأولوية | العمل | دليل الاكتمال المطلوب |
|---|---|---|
| الآن | خادم Cloudflare مستقل: صحة الخدمة، إصدار مخطط الإعداد، وحالة القدرات | اختبارات العقود على GitHub Actions، ثم ردود HTTP فعلية من العنوان المنشور. |
| أول إصدار مستقل | بناء Windows قابل للتكرار، صفحة التحميل، الأصول المتاحة محليًا، دعم Issues، وإزالة اعتماد فحص اتصال التورنت على موقع المطور | بناء المصدر النهائي؛ تشغيل Windows وفحص عدم طلب الموقع القديم. |
| بعده | تحديثات موقعة نملكها، وقنوات stable/beta؛ OAuth للخدمات المختارة | اكتشاف تحديث صحيح وتوقيعه ورفض توقيع خاطئ؛ تجديد تسجيل الدخول دون تسريب رموز. |
| حسب الحاجة | مرحّل Together الموجود في `src-tauri/relay/worker.js` | مراجعة حدود proxy وإصدار البروتوكول والتخزين، ثم اختبار عميلين فعليين. وجود الشيفرة وحده ليس دليل تشغيل عام آمن. |
| لاحقًا | التقارير مع المرفقات، Community Subtitle Sync، ثم مزامنة الملف الشخصي | عقود API، قاعدة البيانات، المصادقة وحدود الاستخدام والنسخ الاحتياطي. |
| يؤجّل | الحسابات الاجتماعية ومتجر الثيمات والحزم وميزات الألعاب والموسيقى والرياضة المعتمدة على خدمة غير موجودة | إعادة تنفيذ backend واختباره قبل تفعيل الواجهة المرتبطة به. |

نحافظ على مزودي Stremio والمشغل والترجمة والمكتبة المحلية. خدمات Stremio وTMDB وغيرها لا تنقل ملكيتها بمجرد تغيير نطاق Harbor. أما بيانات حسابات Harbor القديمة فلا يمكن استعادتها من دون نسخة احتياطية أو تصدير متاح.

## ضمان الاتساق بين جميع الفروع

1. **G1 — عقد إعداد واحد:** نضيف سجلًا بإصدار مخطط يعرّف أدوار الخدمات، عناوينها وقدراتها وقناتي التحديث. تحفظ متغيرات GitHub الخاصة بالمستودع العناوين العامة، وتحفظ Secrets مفاتيح الخادم والتوقيع. لا تُوضع الأسرار في `VITE_*` لأنها تدخل حزمة العميل. [متغيرات GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables)، [متغيرات Vite](https://vite.dev/guide/env-and-mode)
2. **G2 — توليد متسق للعميل:** يقرأ مولّد البناء العقد نفسه لينتج إعدادات TypeScript وRust وإعداد Tauri الإضافي. نستوعب الروابط الصريحة المتبقية: ASR، فحص الاتصال، البريد، `pub` ومقارنة المضيف، التحديث native، الروابط الظاهرة، وبيانات الصور التي تتضمن عناوين مطلقة. تغيير `VITE_HARBOR_API_BASE` وحده لا يغيّر هذه المواضع.
3. **G3 — نقل إلى الرؤوس العشرين:** نعدّ رقعة مهيّأة لكل عائلة كود، ونفتح تغييرًا قابلًا للمراجعة لكل فرع مستهدف بعد الموافقة على التنفيذ. الفروع الأقدم تحتاج إضافة طبقة العناوين أولًا؛ stable/beta تحتاج توسيعها واستبدال المواضع الباقية. لا ندمج ميزات الفرع ضمن رقعة نقل الروابط، ولا نعيد كتابة تاريخه أو نحذفه.
4. **G4 — فحص مركزي عابر للفروع:** يستخرج CI قائمة الفروع الفعلية من GitHub ويقارنها بسجل الترحيل؛ الفرع الجديد يظهر «غير مُرحّل» حتى يجتاز التحقق. يفحص غياب المضيفات القديمة في المواضع التنفيذية والملفات المولّدة، وتطابق أصول الخدمة ومخططها والقنوات. يسمح بإشارات التاريخ في وثائق التدقيق بقائمة سماح محددة. إذا غاب إعداد مطلوب، يوقف الإصدار بدل الرجوع إلى نطاق المطور.
5. **G5 — بوابة إصدار مشتركة:** يستخدم كل فرع قابل للإصدار سير تحقق معاد الاستخدام ومثبت المراجعة، مع تحديث مرجعه بتغييرات مراجعة. الفحص المركزي يلتقط تخلف فرع عن العقد، وبوابة الإصدار تمنع نشر عميل غير متسق. متغيرات المستودع وحدها لا تكفي إن تجاهلها workflow قديم أو تجاوزها إعداد Environment؛ نفحص الناتج الفعلي أيضًا.
6. **G6 — إعدادات المستخدمين:** ننقل تلقائيًا القيم المطابقة للعناوين الافتراضية القديمة فقط. نحافظ على الخادم المخصص الذي أدخله المستخدم، ولا نمسح ملفاته أو حساباته عند تعذر خدمة. إذا تغيّرت هوية تطبيق OAuth، نطلب إعادة التفويض بدل ترحيل رموز إلى خدمة لا تملك تسجيلها الأصلي.

نجاح G3 يعني أن كل رأس مستهدف اجتاز الترحيل أو وُثّق مانعه؛ لا يُعلن اكتمال «جميع الفروع» إذا بقي فرع غير مهيّأ. لا نغيّر معرّف التطبيق `app.harbor` أو مخططات الروابط أو مسارات بياناته ضمن نقل النطاق.

## التعامل مع التحديثات

إعداد Tauri الأصلي يحمل عنوان المطور ومفتاحه العام، بينما واجهة React تفحص الإصدار والتاريخ بعناوين أخرى. يجب نقل المسارين معًا. نستخدم GitHub Releases في مستودعنا لتوزيع الملفات، ونولد بيانات stable/beta من مراجعة المصدر التي اجتازت CI. قناة stable لا تتبع إصدارات beta تلقائيًا.

ننشئ مفاتيح توقيع نملكها، ويبقى المفتاح الخاص في أسرار CI. من دون مفتاح المطور الخاص لا نعد بتحديث تلقائي للنسخ التي تثق بمفتاحه؛ نحتاج مثبت انتقال يدوي أولًا. المثبت الذي بُني سابقًا ما زال يحمل إعداد التحديث القديم لأنه لم يتضمن نقل الخدمات. [توثيق توقيع تحديثات Tauri](https://v2.tauri.app/plugin/updater/#signing-updates)

## سياسة الفروع والميزات

نبقي stable خط الإصدار، وbeta مصدرًا للانتقاء. لا نغيّر الفرع الافتراضي ولا نحذف الفروع القديمة الآن. يمكن لاحقًا أرشفة الفروع المدموجة بعد موافقة المستخدم؛ وحتى ذلك القرار يشملها سجل الترحيل، ولا نعتبر استبعادها حلًا لاتساق الروابط.

- نراجع أولًا إصلاحات المتابعة والطابور والترجمة على stable قبل نقلها؛ كثير من أساسها موجود بالفعل.
- نقيّم فلتر التدفقات المحفوظ وتقييم الحلقة إضافتين مستقلتين، بعد مطابقة اعتمادهما على البيانات والخدمات.
- لا نعيد إضافة SMTC وشاشة التوقف وASS لمجرد وجود فروع تحمل أسماءها؛ لها تنفيذ في stable.
- نؤجل folder hub والتوسعات الكبيرة وميزات غير المشاهدة، وترقية libmpv وإصلاحات المنصات الأخرى، إلى دفعات محددة.

توجد توصية مفصلة لكل فرع في [دراسة الفروع](branches-analysis.md). أعداد الملفات والالتزامات تصف اتساع الفرق؛ لا تثبت وحدها جودة الكود أو غياب ميزة.

## الفحوص وحدود هذه المرحلة

تجري اختبارات الخادم والبناء والتغليف على GitHub-hosted Actions فقط. لا تثبيت أو اختبارات محلية. عند ترحيل العميل لاحقًا نطلب `pnpm run check` وtypecheck لتغييرات TypeScript وCargo check لتغييرات Rust وبناء Linux المطلوب وتعافي انقطاع الخدمات، ثم فحص Windows فعليًا. نسخة stable الحالية تفتقد سكربت `check` أصلًا؛ نسجّل هذا القيد بدل ادعاء نجاح الفحص.

لا نحدّث أدوات التطبيق أو نختار مكتبات backend جديدة ضمن الدراسة. عائلة التقنيات المثبتة: Tauri 2، React 19، TypeScript 5.8 في stable مقابل TypeScript 6 وVite+ في main، وpnpm 11.9.0. اختلاف أدوات الفروع سبب إضافي لتكييف الرقع وفحوصها.

تعرض [خريطة المشروع](../../PROJECT_MAP.md) أدلة البناء والنشر والمعلّقات. الدراسة لا تثبت صحة كل ميزة في وقت التشغيل، ولا تعني أن خدمات المطور السابقة استُعيدت.
